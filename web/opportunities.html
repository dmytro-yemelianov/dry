This page preserves the conversation order and expands it into product, technical and risk areas.

Dry should be a manufacturing compiler before it is a slicer clone.

The current framework is strongest where authored geometry, machine motion, typed IR, verification, optimization and target emit meet. A conventional mesh slicer can be a future frontend; the core product should first make toolpaths inspectable, programmable and safer to push harder.

Core decision

Start with CAD-connected toolpath workbench, post-slicer review, G-code inference and trace analysis. Add full mesh slicing only after the compiler layer is already valuable.

1. Slicer App, CAD Add-On, Broader Uses

Best first wedge: CAD workbench

Export sketches, curves, faces, features or procedural geometry from CAD into Dry L1/L2. Dry owns simulation, verification, optimization and emit.

  • Fusion 360: approachable add-ins.
  • Onshape: cloud and FeatureScript-style workflows.
  • SolidWorks: industrial value, heavier surface.
  • Rhino/Grasshopper: natural procedural toolpath audience.
  • FreeCAD/Blender: open and experimental paths.

Programmable slicer

Path-first rather than STL-first: define exact moves, channel state, orientation and constraints, then compile.

  • Custom infill, lattices and vase modes.
  • Non-planar FFF and rotary/5-axis paths.
  • Gradient material or process experiments.
  • Education and research tooling.

Full slicer later

A full Cura/PrusaSlicer-style app needs mesh repair, offsetting, supports, infill, seam planning, cooling, placement, project formats and many profiles. It is a later frontend, not the initial identity.

Less obvious uses

Robotic extrusion, manufacturing lint in CI, generative-design compiler target, toolpath QA, G-code normalization, fleet policy checks and browser-based print debugging.

2. Existing Slicer / Klipper Pipeline

Dry can sit between existing slicers and the printer. This is a practical near-term product because it adds value without asking users to leave Orca, PrusaSlicer, Cura or Klipper.

Reviewflow, speed, bounds, cooling
Rewritesafe / balanced / max
KlipperMoonraker upload hook

Review-only first

  • Max volumetric flow violations.
  • Feedrates above machine/material profile.
  • Tiny segment density and planner pressure.
  • Travel extrusion, cold extrusion, out-of-bounds moves.
  • Cooling, bridge, overhang and layer-time risk.
  • Suspicious retract/prime or state churn.
dry review part.gcode --profile voron24-abs.json

Rewrite after trust

  • Feedrate and acceleration changes by region.
  • Volumetric-flow-limited speed caps.
  • Redundant state cleanup.
  • Safe collinear merge or arc simplification.
  • Klipper SET_VELOCITY_LIMIT or M204 scheduling.

3. Reverse Engineering And Slicer-Logic Inference

Dry can become a G-code decompiler and slicer-behavior analyzer. It should infer likely rules and structure, not claim perfect reconstruction of CAD intent or private slicer internals.

Parsemodal state + comments
Liftmotion stream -> Dry IR
Classifywalls, infill, bridge, travel
Inferspeed, flow, seam, cooling rules
Explainreport or rewrite policy

Recoverable signals

  • Layer height, line width and extrusion multiplier.
  • Volumetric flow over time.
  • Seam position and infill angle/spacing.
  • Feature speed rules and cooling policy.
  • Retraction, travel and tiny-segment behavior.

Useful methods

  • Curvature, segment-length and duration histograms.
  • Hough/Radon transforms for infill direction.
  • 2D FFT for layer periodicity.
  • STFT/wavelets for local non-stationary behavior.
  • Clustering and changepoint detection.
dry decompile part.gcode -o inferred.dry.json
dry explain part.gcode --profile voron24.json
dry fingerprint part.gcode
dry compare stock.gcode tuned.gcode

4. Time-Series Analysis With LLMs

LLMs should operate around deterministic analysis, not replace it. Dry should compute the signals, summaries and safety checks; an LLM can explain, compare, prioritize and propose experiments.

Deterministic signals

  • x(t), y(t), z(t), e(t).
  • Speed, acceleration, jerk estimate.
  • Volumetric flow and segment rate.
  • Curvature, layer index and feature class.
  • Fan, temperature and channel state.
  • Frequency summaries, anomalies and changepoints.

LLM role

  • Explain why a print is slow or risky.
  • Translate analysis into profile changes.
  • Compare stock vs tuned G-code.
  • Suggest calibration experiments.
  • Draft a safe optimization policy for verifier approval.

Suggested Sequence

G-code parser

Lossless modal state and source-line mapping.

Review-only reports

Flow, speed, bounds, temp, segment density, cooling and structural checks.

Profile schema + Klipper hook

Versioned machine/material profiles and Moonraker upload integration.

Trace export and compare

Efficient time-series data plus stock-vs-tuned diff reports.

Conservative rewrite mode

Redundant state cleanup and safe feed caps, fully verified.

Inference and LLM explanations

Feature classification, rule inference and human-readable recommendations.

CAD/plugin workbench

Fusion, Onshape, Rhino/Grasshopper or FreeCAD path export into Dry.

Calibrated max mode

Aggressive optimization based on measured flow, accel, cooling and resonance envelopes.

Hybrid mesh slicer

Use existing geometry kernels for conventional slicing when the compiler layer is already proven.
